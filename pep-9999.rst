Abstract
========

High performance virtual machines for dynamic languages achieve their
performance in many ways. Usually, the VM performs type profiling and
detects hotspots before optimizing "hot" regions of code.

This PEP provides an API for plugging in an optimizer to the CPython virtual
machine, that lets the virtual machine select which points in the code merit
optimization, but leave it to the optimizer to perform that optimization.

This PEP renders PEP 523 obsolete, and the interface specified by
PEP 523 will be removed.

Motivation
==========

The existence of Cinder [2] and Pyston [3] shows that there is the ability
and willingness to produce an optimizer for CPython. However, the JIT compiler in
Cinder is tied to Cinder specifics and cannot be reused for CPython.
Likewise for Pyston. By providing an API that allows the optimizer to focus on
optimization, we can have better optimizers that work more effectively
with the rest of the virtual machine.

Rationale
=========

Since optimization occurs at runtime, it makes sense to optimize only those
sections that are "hot", that are likely to executed many times.
The key to optimization of dynamic languages is specialization, where code
is optimization in a way that speculates the types and values it will encounter.

For optimization to work, the VM needs to monitor the performance characteristics
of the program and to gather profiling information *before* optimization.

Therefore, we want the VM to responsible for deciding when to optimize, and
from where, and to have gathered sufficient profiling information before it
requests the optimizer to do its job. 

It is then up to the optimizer to optimize some region of code from the given
starting point, and using the gathered information. It is up to the 
optimizer how it uses that information and the extent of the region it
optimizes.

The provided API allows the VM to control when and where optimization occurs,
and allows the optimizer to decide how it occurs.

PEP 523 has this back-to-front, and ends up preventing some optimizations, 
specifically cross-call optimizations. It also limits optimizers to 
optimizing one entire function at a time.

Specification
=============


The following structs and functions will be added to the unstable C-API::

    type struct {
        OBJECT_HEADER;
        _PyInterpreterFrame *(*execute)(PyExecutorObject *self, 
                                        _PyInterpreterFrame *frame,
                                        PyObject **stack_pointer);
        /* Data needed by the executor goes here, but is opaque to the VM */
    } _PyExecutorObject;

    typedef enum {
        FUNCTION_ENTRY = 1,
        BACK_EDGES = 2,
        ANY_INSTRUCTION = 7 /* Implies both the above */
    } _PyOptimizerCapabilities;

  typedef enum _compilation_result {
      FAILURE = -1,
      SUCCESS = 0,
      DECLINED = 1,
      DEFERRED = 2,
  } _PyOptimizationResult;

    type struct {
        OBJECT_HEADER;
        _PyOptimizationResult (*optimize)(PyOptimizerObject* self, 
                                          PyCodeObject *code, int offset, 
                                          PyExecutorObject **result);
        int capabilities; /* Bitwise or of PyOptimizerCapabilities */
        float optimization_cost;
        float run_cost;
        /* Data needed by the compiler goes here, but is opaque to the VM */
    } _PyOptimizerObject;

    void _Py_Executor_Replace(PyCodeObject *code, int offset, PyExecutorObject *executor);

    int _Py_Optimizer_Register(_PyOptimizerObject* optimizer);

The ``optimize()`` function pointer in the ``_PyOptimizerObject`` should behave as follows:

If returning ``SUCCESS`` the ``result`` should be a ``_PyExecutorObject``. ``result`` should be untouched otherwise.
if returning ``FAILURE``, an ``Exception`` should be set.

If ``DECLINED`` is returned, then the VM will not attempt to optimize at this point again.
If ``DEFERRED`` is returned, then the VM may attempt to optimize from this point in the future.

The ``execute`` function takes the current frame and stack pointers. When the ``execute`` function is called, the
VM will ensure that all VM state is correct and in memory, *except* the stack pointer, which is passed
as an arguments. On return all the VM state must be correct and in memory.
If an exception has been raised, ``execute()`` must return NULL.
If no exception has been raised, ``execute()`` must the current frame pointer, which must be consistent with memory.

Removal of PEP 523 and porting PEP 523 based optimizers
=======================================================

If this PEP is accepted all data structures and functions that are part of PEP 523 will be removed.

Optimizers using PEP 523 can be ported to this API roughly as follows:

The ``execute()`` function can delegate to old PEP 523 evaluate function::

    _PyInterpreterFrame *execute(PyExecutorObject *self, _PyInterpreterFrame *frame, PyObject **stack_pointer);
        _PyFrame_SetStackPointer(frame, stack_pointer);
        PyObject *retval = pep523_eval(tstate, frame);
        if (retval == NULL) {
            return NULL;
        }
        return tstate->cframe->current_frame;
    }

The ``capabilities`` should be set to ``FUNCTION_ENTRY`` only.

Data that would have been stored in ``co_extra`` can now be stored in the ``_PyExecutorObject``::

    type struct {
        PY_EXECUTOR_HEAD;
        void *co_extra;
    } _PyPEP523ExecutorObject;

In practice, in is unlikely that any optimizer will use this approach, as method-at-time JITs like
Cinder use the vectorcall protocol to replace the function's vectorcall with custom machine code.

Implementation outline
======================

Finding hotspots
----------------

This can be done with two counters. One on backedges and function entry points,
and one global counters. We hit a hotspot when the code is executed frequently.
The frequency we need to reach depends on the optimization_cost and run_cost
of the optimizer, as well as how long the program has been running,
optimize when frequency > threshold.
frequency = delta(local counter)/delta(global counter).
threshold = N*(1/((global counter)+1)) + M*optimization_cost/run_cost where M
and N are tunable parameters.

We check frequency whenever the local counter hits 0.
Since we started the local counter at some constant K,
then delta(local counter) == K. If we store the value of the global
counter when the local counter was set to K,
then we have frequency = K/((global counter) - (local value of global counter))

With C = M*optimization_cost/run_cost
frequency > threshold is equivalent to
K/((global counter) - (local value of global counter)) > N*(1/((global counter)+1)) + C
It is then just algebra, to re-organize the above equations into an efficient test of frequency > threshold.

Entering executor objects
-------------------------

Once we have hit a hotspot and got a PyExecutorObject,
we need to transfer execution to it.
Once again, we use our ability to replace instructions at runtime.
Given that any potential hotspot needs space for counters,
we can reuse that space to point to a PyExecutorObject
and replace the JUMP_BACKWARD with an ENTER_EXECUTOR opcode::

    TARGET(ENTER_EXECUTOR) {
        _PyExecutorCache *cache = (_PyExecutorCache *)next_instr;
        PyExecutorObject *executor = read_obj(cache->executor);
        frame = executor->execute(executor, frame, stack_pointer);
        assert(cframe.current_frame == frame);
        goto resume_frame;
    }

The equivalent version for function entry would replace RESUME
and probably store the executor on the code object, not inline.


Open Issues
===========

The high level interface requires the optimizer to decide what region to compiled, and
requires the compiler to understand the state of the VM to make that decision.

In future we may add a low-level compiler interface which explicitly tells the compiler
what region to compile, possibly passing some intermediate representation of that region.
